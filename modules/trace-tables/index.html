2. Understanding Program Errors

Find, diagnose, and fix Python syntax, logic, and runtime errors. Use the interactive code scratchpad to repair defects directly in the code and verify your fixes in the live terminal.

1. Syntax Errors PRE-RUN HALT

Syntax is the spelling and grammar of a programming language. Programming languages have rules for spelling, punctuation and grammar, just like the English language.

Syntax errors include:
  • incorrectly spelled statements, keywords, or variable names
  • missing punctuation (quotes, brackets, colons :, etc.)
while points > 0 # missing ':' SyntaxError: expected ':'
2. Logic Errors 0 CRASHES / WRONG RESULT

A logic error occurs when the code runs without crashing, but doesn't do what the programmer intended (produces the wrong output).

Logic errors include:
  • using the wrong operator (e.g. < instead of <=)
  • incorrect formula or calculation
  • infinite loops where a counter variable never updates
points = 5
while points > 0:
    discount = discount + 2
    points = points  # missing decrement (- 1)
[Timeout: Infinite loop]
3. Runtime & Type Errors CRASHES MID-RUN

A runtime error occurs while the program is actively executing. The syntax is valid, but the CPU is directed to execute an impossible operation.

Runtime errors include:
  • division by zero (x / 0)
  • incompatible data types (adding str to float)
  • accessing a list item that doesn't exist (index out of range)
price = 12.50
fee = "5.00"
total = price + fee  # incompatible types!
TypeError: float + str

3. Test Plans & Boundary Testing

Even when a program runs without errors it can still produce the wrong results. This is why testing is important. A test plan should include testing valid, erroneous and boundary thresholds to see if the output matches the expected result.

1. Normal (Valid) Data TYPICAL

Sensible data well inside the acceptable domain range. Expected to execute and pass smoothly (e.g. 12 hrs on a 1–24 hr rental).

2. Boundary (Extreme) Data EXACT EDGES

Values on the exact perimeter threshold limits (e.g. exactly 1 hr and 24 hrs). Crucial because developers regularly make comparison bugs (< vs <=).

3. Erroneous Data INVALID

Completely invalid inputs breaching domain bounds or data types (e.g. 0 hrs, 35 hrs, negative numbers, or non-numeric strings). Must be safely rejected.

1. Structuring programmes

Decomposition breaks complex problems down into self-contained sub-problems, which are organized into structured subroutines. Functions and procedures communicate cleanly using parameters and return values, creating reliable software that is easy to build, test, and understand.

Why Modular? The Car Analogy
MODULAR ARCHITECTURE Tap to read ▾

Imagine if car manufacturers forged an entire vehicle as a single, solid lump of welded metal. If a headlight burned out or a tyre popped, you would have to scrap the whole vehicle! Instead, cars are assembled from pre-tested, interchangeable parts: braking callipers, alternator, and engine blocks. Crucially, a well-engineered modular component like a wheel, battery, or engine can also be reused in another car model without redesigning it from scratch. In software, writing everything in one giant monolithic script is just as dangerous. Programmers use Decomposition to break complex systems down into independent, reusable Subroutines that can be shared across programs.

1. Monolith (Raw Mess)

500 lines in one huge file. If line 10 crashes, the whole system dies. Impossible to test in pieces or share across a team.

2. Subroutines (Modular Parts)

Independent, single-purpose functions & procedures: check_abs(), calc_pressure(), apply_brakes(). Reusable in other vehicles!

            🧩 Modular Programming & Architecture
          


          

            

              

                

                  
                

                
What is Decomposition?

              

              

                Breaking down a complex problem or software system into smaller, self-contained sub-problems. Each sub-problem is simpler to design, write, test, and debug independently.
              

            


            

              

                

                  
                

                
What is a Subroutine?

              

              

                A named, self-contained block of instructions performing one specific task. Subroutines are divided into Functions (which return a value) and Procedures (which do not return a value).
              

            


            

              

                

                  
                

                
Benefits of modular code

              

              

                1. Reusability: Call subroutines repeatedly or in other programs without copy-pasting code.

                2. Easier Debugging: Isolate bugs to one subroutine.

                3. Unit Testing: Test modules in isolation.

                4. Teamwork: Programmers work on separate modules concurrently.
              

            


            

              

                

                  
                

                
Parameters & Scope

              

              

                Parameters pass data down into subroutines. Return values pass results back to the caller. Local variables exist only while the subroutine runs, avoiding variable clashes and bugs from unintended global changes.
              

            

          

        


        
        

          🔍 Testing, Debugging & Trace Tables
        


        
        

          

            RULE 1: TRACE TABLE CONVENTIONS
            Paper 1 Essential
          

          

            Golden Rules for Completing Exam Trace Tables
          

          

            Examiners mark trace tables using strict coordinate grids. Remember these 3 rules to avoid losing marks:
          

          

            

              1. Only Write on Value Changes: Do not rewrite a variable's value on a new line if it has not changed. Leave blank spaces until a reassignment happens.
            

            

              2. Dedicated Output Column: Only write values in the Output column when a print/display statement explicitly executes. Never write calculation intermediates here.
            

            

              3. Condition Columns: When the exam includes condition evaluation columns (e.g. x < 5), write TRUE or FALSE clearly.
            

          

        


        
        

          

            RULE 2: TEST DATA STRATEGIES
            3 Required Categories
          

          

            Normal vs Boundary vs Erroneous Test Data
          

          

            Suppose a program accepts pupil exam percentages from 0 to 100 inclusive:
          

          

            

              Normal (Valid) Data: Sensible test inputs that fall safely within the expected range (e.g. 45, 72, 88). Should be accepted smoothly.
            

            

              Boundary (Extreme) Data: Values on the exact edge limits of acceptability, plus just outside (e.g. 0, 100 and outside -1, 101). Catches off-by-one errors.
            

            

              Erroneous (Invalid) Data: Values of incorrect data type or clearly illegal inputs (e.g. "seventy", -25, null). The program should reject them with validation errors.
            

          

        


        
        

          

            RULE 3: ERROR CLASSIFICATION
            Common Trap
          

          

            Syntax vs Logic vs Runtime Errors
          

          

            

              Syntax Error: Breaks grammatical programming rules (e.g. spelling prnt("hi") or missing colon/brackets). Detected by the interpreter before running.
            

            

              Logic Error: The program compiles and runs without crashing, but outputs the wrong answer (e.g. using + instead of -, or < instead of <=).
            

            

              Runtime Error: An illegal operation causes the program to crash abruptly while executing (e.g. dividing by zero, file not found, index out of range).
            

          

        


        
        

          

            RULE 4: SUBROUTINE CLASSIFICATION
            Core Vocabulary
          

          

            Functions Return Values; Procedures Do Not
          

          

            In GCSE pseudocode and programming languages, subroutines are split into two categories based on output behavior:
          

          

            

              Function: Must include a return statement that sends data back to the expression where it was called (e.g. area = calculateArea(5, 10)).
            

            

              Procedure: Executes actions (e.g. displayMenu() or saving to disk) but does not send a value back to the caller.
